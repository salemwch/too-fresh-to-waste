## How these are classified

The distinction that matters is **accessibility blocker** versus **consistency
improvement**, because only the first can hold up certification.

| Class                         | Meaning                                                                                    |
| ----------------------------- | ------------------------------------------------------------------------------------------ |
| **Accessibility blocker**     | A measured WCAG failure on a surface a user actually reaches                               |
| **Accessibility - contested** | A measured shortfall against a criterion whose intent is arguably met by other affordances |
| **Consistency**               | Two values differ, or a value is off-scale. No user is harmed                              |
| **Performance**               | A runtime cost, not a rendering defect                                                     |
| **Product / brand**           | The "right" answer depends on intent, not on measurement                                   |

**A cross-platform difference is not, by itself, a reason to migrate.** Web and
mobile are different products with different constraints; D5 is the clearest
case and is recommended for documentation rather than change.

## D1. Coral cannot carry light text

|                                              |                                                                                                                                                                                                                                                                                              |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Current implementation**                | `--accent: 4 90% 62%` (`#F55347`), `--accent-foreground: 0 0% 98%` (`#FAFAFA`). Same shape on `--destructive: 0 84% 60%` (`#EF4343`).                                                                                                                                                        |
| **2. Why it exists**                         | Coral is the brand accent. Pairing it with near-white is the conventional filled-button treatment and was never measured.                                                                                                                                                                    |
| **3. Accessibility impact**                  | **Measured at HEAD: `#FAFAFA` on `#F55347` = 3.24. AA text needs 4.5. Fails.** Destructive is **3.62**, also fails. Dark ink would give **5.78** and **5.17** respectively. (`DESIGN.md` records 3.38/3.78; those used pure white. Both sets of figures fail - the conclusion is unchanged.) |
| **4. UX impact**                             | Affects any coral surface carrying a label: `Button variant="ghost"` hover, destructive buttons, the highlighted item in an open `Select`. Low-vision users lose the label, not the button.                                                                                                  |
| **5. Visual impact**                         | Option (a) dark-on-coral reads unusual for a destructive control. Option (b) darkens the fill and keeps white text, which is a visible brand shift on every coral CTA.                                                                                                                       |
| **6. Affected components/routes**            | `Button` (ghost hover, destructive), `Select` highlighted item, `Alert` destructive, `Badge` accent. All are shadcn primitives used product-wide.                                                                                                                                            |
| **7. Existing visual coverage**              | **Strong.** `button`, `button-focus`, `select-open-selected`, `alert`, `badge` are all in the 156 component baselines, at 12 combinations. `select-open-selected.png` already shows the failing white-on-coral state.                                                                        |
| **8. What changes under the recommendation** | `--destructive` and the text-bearing coral fill darken to an existing ramp step (`error-600 #C62828`, **5.62** with white text). Coral CTAs become perceptibly deeper.                                                                                                                       |
| **9. What does not change**                  | Coral stays the brand accent for **icons, borders, indicators and non-text marks**, which only need 3:1 under 1.4.11 and already pass. The ramp is not redefined. `accent-500` stays where it is for non-text use.                                                                           |
| **10. Migration risk**                       | **Low-medium.** Token-level, one value. The baselines will show every affected primitive before it ships. Risk is aesthetic acceptance, not breakage.                                                                                                                                        |
| **11. Required for certification**           | **Yes.** This is the only measured AA text failure on a reachable surface.                                                                                                                                                                                                                   |
| **12. Recommended decision**                 | **Option (b): darken the fill for text-bearing surfaces, keep brand coral for non-text marks.** It preserves white-on-red, which is what a destructive action is expected to look like.                                                                                                      |
| **13. Alternative**                          | Option (a) dark ink on the existing coral - passes at 5.78, no brand shift, but a red button with dark text reads unusual. Option (c) reserve coral for non-text entirely - passes, but removes coral CTAs.                                                                                  |
| **14. Now or exception?**                    | **Implement now.** An AA text failure is not eligible to be an intentional exception.                                                                                                                                                                                                        |

## D2. `border` is 1.24:1 against white

|                                              |                                                                                                                                                                                                                                                                                                                                                                        |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Current implementation**                | `--border` and `--input` = `174 8% 90%` = `#E3E8E7`.                                                                                                                                                                                                                                                                                                                   |
| **2. Why it exists**                         | A soft hairline is the house look; it was chosen visually, not measured.                                                                                                                                                                                                                                                                                               |
| **3. Accessibility impact**                  | **Measured: 1.24 against white. WCAG 1.4.11 asks 3:1 for "visual information required to identify a component".** The contested part is the word _required_: an input here also has a persistent label, placement, a placeholder, and a focus ring at `--ring: 186 41% 20%`. If those identify the control, the border is decoration and 1.4.11 is arguably satisfied. |
| **4. UX impact**                             | In bright light or on a poor panel, field boundaries are hard to see. Affects form-dense pages most.                                                                                                                                                                                                                                                                   |
| **5. Visual impact**                         | Darkening `--border` globally changes every card edge, divider and table rule - a heavier, more clinical product. Darkening only `--input` changes forms alone.                                                                                                                                                                                                        |
| **6. Affected components/routes**            | `--input`: `Input`, `Select`, `Textarea`, `Form`. `--border`: additionally `Card`, `Separator`, `Dialog`, `Tabs`.                                                                                                                                                                                                                                                      |
| **7. Existing visual coverage**              | **Strong.** `input`, `input-focus`, `form`, `select`, `card`, `separator`, `tabs`, `dialog-open` are all covered at 12 combinations.                                                                                                                                                                                                                                   |
| **8. What changes under the recommendation** | Only `--input` darkens to a value that measures >= 3:1. Form fields gain a visible boundary.                                                                                                                                                                                                                                                                           |
| **9. What does not change**                  | `--border` keeps its current value, so cards, dividers and table rules are untouched. The house look survives where it is decorative.                                                                                                                                                                                                                                  |
| **10. Migration risk**                       | **Low** if scoped to `--input`. **Medium** if `--border` moves too, because it touches every surface.                                                                                                                                                                                                                                                                  |
| **11. Required for certification**           | **No.** This is a contested reading of 1.4.11 with named compensating affordances, not an unambiguous failure like D1.                                                                                                                                                                                                                                                 |
| **12. Recommended decision**                 | **Darken `--input` only, to a measured >= 3:1 value from the existing neutral ramp.** Do not invent a hex. Leave `--border` alone.                                                                                                                                                                                                                                     |
| **13. Alternative**                          | Formal acceptance in §19-E4, naming label + placement + focus ring as the compensating affordances. This is what most design systems do and is defensible - but it must be written down, not assumed.                                                                                                                                                                  |
| **14. Now or exception?**                    | **Either is legitimate.** If not implemented, upgrade E4 from `UNRESOLVED` to `ACCEPTED` with the affordances named. Leaving it `UNRESOLVED` indefinitely is the one bad option.                                                                                                                                                                                       |

## D3. `/parcless-bag` runs a parallel palette

|                                              |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Current implementation**                | **38 raw hex** in `ParclessBagClient.tsx` (the `page.tsx` itself has none). Five values exist in no token file: `#F2EBD9` (14), `#7FA896` (8), `#C05F4A` (5), `#3D6B5C` (5), `#3A4F48` (2).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **2. Why it exists**                         | One marketing page was designed as its own artefact. Whether that was sanctioned is exactly the open question.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **3. Accessibility impact**                  | **AUDITED 2026-09-01 - see `.claude/work/parcless-bag-palette-audit.md`.** Every occurrence measured against its real ground, not a representative one. **All 8 sage usages are body text on `bg-primary`, at 3.23-4.02 - all fail AA.** (The earlier 2.22 figure measured sage on cream, a ground it is never painted on; superseded.) **Terracotta: 3 body-text usages at 3.55 on cream, 2 background usages that are fine at 3:1, and 3 white-on-terracotta strings at 3.37-4.22 that are not.** Deep green 7.38, mid green 5.11, ink 14.74 still pass. **Dark theme is worse: `bg-primary` inverts to `#54ACB6` and sage does not, giving 6 strings a ratio of 1.00 - invisible.** |
| **4. UX impact**                             | None in isolation - the page is self-consistent. The cost is brand coherence: a visitor moving from this page to the rest of the site sees a different product.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **5. Visual impact**                         | Mapping to existing tokens changes how the page looks, and it was presumably signed off as-is. Promoting to `brand.*` blesses a second palette permanently.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **6. Affected components/routes**            | One route: `/[locale]/(marketing)/parcless-bag`. One component file.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| **7. Existing visual coverage**              | **12 baselines, added 2026-09-01.** `parcless-bag` is now in `routes.spec.ts` (3 viewports x light-en / dark-en / light-ar / light-fr). Viewport-only at scroll 0, so it pins the hero and the theme-dependent ground; everything below the fold is still uncovered.                                                                                                                                                                                                                                                                                                                                                                                                                   |
| **8. What changes under the recommendation** | Nothing visual. The five values are documented as a sanctioned one-page palette with their measured ratios and a usage constraint on sage and terracotta.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **9. What does not change**                  | The page renders identically. No token file grows.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **10. Migration risk**                       | **Low** to document. **Medium** to remap, because there is no baseline to catch what moves.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **11. Required for certification**           | **YES.** The caveat fired. Both colours carry normal body text in failing combinations - 11 of 14 text roles across the two fail AA at their real grounds, and sage is invisible in dark mode. This is an AA failure, so it is not eligible to be an intentional exception, independently of the brand question.                                                                                                                                                                                                                                                                                                                                                                       |
| **12. Recommended decision**                 | **Fix the text roles; the brand question stays open.** The audit is done and the baseline is added. Remedy is still a product/brand call: map to tokens, promote to `brand.*` with passing text variants, or keep sage and terracotta for surfaces and darken them for text. Dark mode needs its own answer, since the ground moves and the foreground does not.                                                                                                                                                                                                                                                                                                                       |
| **13. Alternative**                          | Remap to existing tokens - restores one palette, changes a signed-off page, and needs a baseline created first.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **14. Now or exception?**                    | **Now.** The condition was tested and failed. An AA text failure cannot be filed as an intentional exception.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

## D4. `.glass` on the merchant dashboard

|                                              |                                                                                                                                                                                                                                                                    |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **1. Current implementation**                | `.glass` = `background: rgba(255,255,255,0.55)` + `backdrop-filter: blur(20px) saturate(140%)` + a 1px translucent border. **76 usages across 16 files**, all merchant dashboard.                                                                                  |
| **2. Why it exists**                         | A frosted-card aesthetic for the dashboard.                                                                                                                                                                                                                        |
| **3. Accessibility impact**                  | **None measured.** A translucent ground can reduce text contrast, but contrast here has not been measured, because the routes are behind auth and no baseline exists. **Unverified, not cleared.**                                                                 |
| **4. UX impact**                             | `backdrop-filter` on a **scrolling** surface repaints everything behind it every frame. On low-end hardware this is the difference between smooth and janky. `DESIGN.md` §7.5 permits it only on the fixed header and modal overlays, so all 76 are out of policy. |
| **5. Visual impact**                         | Removing it is not a refactor - 76 cards stop being frosted and become solid. That is a redesign of the dashboard's surface treatment.                                                                                                                             |
| **6. Affected components/routes**            | 16 files: merchant community / esg / leaderboard pages, plus analytics, inventory, loyalty, payments, reviews, settings, impact-cards, campaign-side-panel, streak-widget, trend-chart, reporting-bar, dashboard-welcome-header, location-switcher.                |
| **7. Existing visual coverage**              | **None.** No authenticated route has a baseline. This is the single largest blind spot in the web suite.                                                                                                                                                           |
| **8. What changes under the recommendation** | Nothing. §7.5 is amended to record the dashboard as a sanctioned exception, with the repaint cost stated.                                                                                                                                                          |
| **9. What does not change**                  | The dashboard looks and performs exactly as it does today.                                                                                                                                                                                                         |
| **10. Migration risk**                       | **High** to remove - 76 surfaces change with no baseline to check them against, on routes only reachable by logging in.                                                                                                                                            |
| **11. Required for certification**           | **No.** It is a performance and policy question, not a measured user-facing defect.                                                                                                                                                                                |
| **12. Recommended decision**                 | **Document as an intentional exception in §7.5**, and separately measure text contrast on a glass card so the accessibility question stops being open. Establish authenticated baselines before any removal is attempted.                                          |
| **13. Alternative**                          | Restyle the dashboard to solid cards - better performance and back within policy, but a visible redesign that should be a deliberate product decision, not a cleanup.                                                                                              |
| **14. Now or exception?**                    | **Exception now.** Revisit if dashboard performance is reported as a problem, or once authenticated baselines exist.                                                                                                                                               |

## D5. The `accent` ramp differs between web and mobile

|                                              |                                                                                                                                                                                                                                                                                                             |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Current implementation**                | Web and mobile agree on `50` (`#FFF5F4`), `500` (`#F55449`) and `900` (`#751A13`). **The other seven steps differ.** Web is a clean tint/shade progression around 500. Mobile's `300` is `#F04535` - a distinct saturated coral, not a tint - and its `400` (`#FF5A52`) is _darker_ than web's (`#FF9F97`). |
| **2. Why it exists**                         | The two ramps were authored independently for two products. Mobile's `300` is used as a brand accent in its own right.                                                                                                                                                                                      |
| **3. Accessibility impact**                  | **None.** Both platforms' `accent-700` clear AA. No step in either ramp is used in a failing pairing that has been measured.                                                                                                                                                                                |
| **4. UX impact**                             | **None for any user.** No user sees both ramps. The cost is entirely to developers: a component ported between platforms changes colour at every non-500 step.                                                                                                                                              |
| **5. Visual impact**                         | Unifying would change one platform's coral at seven steps - a visible brand change on whichever side loses.                                                                                                                                                                                                 |
| **6. Affected components/routes**            | Anything using `accent-100..400` or `600..800` on either platform.                                                                                                                                                                                                                                          |
| **7. Existing visual coverage**              | Web: strong at the component level. Mobile: 422 style snapshots would catch token changes. So a unification **is** verifiable - but that is not a reason to do it.                                                                                                                                          |
| **8. What changes under the recommendation** | Nothing in code. `DESIGN.md` §19-E18 records the divergence as accepted, states which ramp is canonical **per platform**, and warns that porting a component requires re-checking non-500 accent steps.                                                                                                     |
| **9. What does not change**                  | Both ramps, both products, every rendered colour.                                                                                                                                                                                                                                                           |
| **10. Migration risk**                       | **Medium-high for zero user benefit.** Seven token steps on a live brand colour.                                                                                                                                                                                                                            |
| **11. Required for certification**           | **No.**                                                                                                                                                                                                                                                                                                     |
| **12. Recommended decision**                 | **Document as an intentional exception. Do not migrate.** Two platforms holding different values is not a defect. The open question - "is `accent-300` a tint of coral or a second coral?" - only needs answering if someone wants to unify; it does not need answering to ship.                            |
| **13. Alternative**                          | Unify on one ramp. Only worth it if a shared component library across web and mobile becomes real; today it is a rename with a brand cost.                                                                                                                                                                  |
| **14. Now or exception?**                    | **Exception.** Revisit only if cross-platform component sharing is actually adopted.                                                                                                                                                                                                                        |

## D6. Radius scales are transposed

|                                              |                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Current implementation**                | Web `md` 12px, `lg` = `var(--radius)` = `0.5rem` (8px), `xl` 20px, `2xl` 24px. Mobile `md` 8, `lg` 12, `xl` 16, `2xl` 20. §6.1 declares **mobile's canonical**. `md` and `lg` are transposed between them.                                                                                                                                                                                                                                                |
| **2. Why it exists**                         | The two scales were authored independently. §6.1 picked a winner after the fact; the code never followed.                                                                                                                                                                                                                                                                                                                                                 |
| **3. Accessibility impact**                  | **None.** Corner radius carries no accessibility requirement.                                                                                                                                                                                                                                                                                                                                                                                             |
| **4. UX impact**                             | **None for users.** A developer reading `rounded-lg` gets 8px on web and 12px on mobile, which is a correctness trap when porting.                                                                                                                                                                                                                                                                                                                        |
| **5. Visual impact**                         | **Large and product-wide.** `--radius` moves `0.5rem` -> `0.75rem`. Buttons, inputs, selects, tabs and tooltips go 12px -> 8px (**sharper**); cards, dialogs and alerts go 8px -> 12px (**softer**). They swap.                                                                                                                                                                                                                                           |
| **6. Affected components/routes**            | Measured at HEAD: `rounded-md` - `button`, `input`, `select`, `tabs`, `tooltip`. `rounded-lg` - `card`, `dialog`, `alert`. Unaffected: `badge`, `avatar` (`rounded-full`), `separator`, and every `rounded-sm`. Every route, public and authenticated.                                                                                                                                                                                                    |
| **7. Existing visual coverage**              | **Strong, and better than previously recorded.** Eight of the thirteen covered components - button, button-focus, input, input-focus, select, select-open, card, dialog-open, tabs, alert - use exactly the two classes that move, at 12 combinations each. **A radius change would be demonstrated before it ships.** What the baselines will not show is those primitives _in situ_: 3 routes have an image of record, and no authenticated route does. |
| **8. What changes under the recommendation** | `--radius` and the `md`/`lg` keys align to §6.1. Every button and input gets sharper; every card and dialog gets rounder.                                                                                                                                                                                                                                                                                                                                 |
| **9. What does not change**                  | `xs`, `sm`, `full`, the mobile scale (already canonical), and any component using `rounded-sm` or `rounded-full`.                                                                                                                                                                                                                                                                                                                                         |
| **10. Migration risk**                       | **Low mechanically, high perceptually.** A config change with excellent component-level evidence - but every corner in the product moves, and the composed pages are largely unverified.                                                                                                                                                                                                                                                                  |
| **11. Required for certification**           | **No.** Pure consistency.                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **12. Recommended decision**                 | **Implement when there is appetite for a product-wide visual change - not before, and not as part of a cleanup.** The blocker was previously described as evidence; it is not. The evidence exists at component level. The blocker is **approval**: someone has to want every corner to change.                                                                                                                                                           |
| **13. Alternative**                          | Amend §6.1 to declare the two scales independent and drop the unification goal. Legitimate, and cheaper - but then `rounded-lg` permanently means two different things, which is the trap that caused this entry.                                                                                                                                                                                                                                         |
| **14. Now or exception?**                    | **Neither yet - it needs a yes.** If the answer is no, take the alternative and amend §6.1 rather than leaving it `PLANNED` forever.                                                                                                                                                                                                                                                                                                                      |

## D8. Remaining `left-` / `right-` offsets

|                                              |                                                                                                                                                                                                                                        |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Current implementation**                | **65 `left-*` and 56 `right-*` across 38 files** (re-measured 2026-08-31; the original entry said 62/53). Margin and padding are fully converted: `ml-*`/`mr-*` = **0**, `pl-*`/`pr-*` = **2**.                                        |
| **2. Why it exists**                         | The V9 pass converted 106 margin/padding/text-align utilities and **deliberately stopped** at absolute offsets, which need per-site judgement.                                                                                         |
| **3. Accessibility impact**                  | **None directly.** Indirectly, a mis-mirrored control in Arabic is a usability defect for RTL users, which is why this is not purely cosmetic.                                                                                         |
| **4. UX impact**                             | Unknown per-site. Some of the 121 are direction-neutral pairs (`left-0 right-0`), some sit in SVG or LTR-locked content, and some are coupled to a sibling's padding - the case that produced the `SelectItem` check-indicator bug.    |
| **5. Visual impact**                         | Correct conversions are invisible in LTR and fix Arabic. Incorrect ones break LTR, which is exactly how the `text-align` regression (§19-E21) happened.                                                                                |
| **6. Affected components/routes**            | 38 files across components and routes.                                                                                                                                                                                                 |
| **7. Existing visual coverage**              | **Partial and useful.** Arabic baselines exist at all three viewports (`desktop-light-ar`, `tablet-light-ar`, `mobile-light-ar`) for 13 components - so component-level mirroring is verifiable. Route-level RTL coverage is 3 routes. |
| **8. What changes under the recommendation** | Nothing at once. A reviewed pass converts only the offsets confirmed direction-sensitive, in small batches, each checked against the ar and en baselines.                                                                              |
| **9. What does not change**                  | Direction-neutral pairs, SVG internals and LTR-locked content stay physical - correctly.                                                                                                                                               |
| **10. Migration risk**                       | **High if done as a codemod, low if done in reviewed batches.** There is direct precedent for the codemod approach causing a regression.                                                                                               |
| **11. Required for certification**           | **No.** Radix direction is fixed (D7/E22), and RTL mirroring was verified on mobile. No specific mis-mirroring defect is currently recorded against these 121.                                                                         |
| **12. Recommended decision**                 | **Reviewed pass, batched, never a blind codemod.** Prioritise the files with the most `left-`/`right-` occurrences and any Arabic-visible component.                                                                                   |
| **13. Alternative**                          | Accept permanently and document that absolute offsets are exempt. Weak - it guarantees the next RTL bug is in this set.                                                                                                                |
| **14. Now or exception?**                    | **Neither urgent nor an exception - schedule it.** Low risk in batches, real payoff for Arabic, no reason to rush.                                                                                                                     |

## OfferCard width (mobile)

|                                              |                                                                                                                                                                                                                                                                           |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Current implementation**                | `OfferCard.styles.card` sets `maxWidth: 270` for the vertical orientation (`180` horizontal), `minWidth: 170`. Applies to **every vertical `OfferCard`**, regardless of container.                                                                                        |
| **2. Why it exists**                         | The card was designed for Home's horizontal carousels, where 270dp is right. The cap travelled with the component into a full-width vertical list.                                                                                                                        |
| **3. Accessibility impact**                  | **None.** No contrast, target-size or scaling implication.                                                                                                                                                                                                                |
| **4. UX impact**                             | On Favorites the card renders **405px in a 624px row, left-aligned at x=48, leaving 35% of the row empty**. It reads as unfinished rather than as a deliberate narrow card.                                                                                               |
| **5. Visual impact**                         | Measured by device width: **320dp 0% unused, 390dp 17%, 430dp 26%, 480dp 35%.** Invisible on the narrowest phone and worsening with size - which is why it was never caught.                                                                                              |
| **6. Affected components/routes**            | **Favorites** (confirmed by measurement). **Home** is unaffected - 270dp is the intended carousel width. **Search** is likely affected and **was not measured**.                                                                                                          |
| **7. Existing visual coverage**              | **None. `OfferCard` has no snapshot coverage** - only `offerCardHelpers.test.ts`. This is the weakest evidence position of any decision here.                                                                                                                             |
| **8. What changes under the recommendation** | Under Option A the vertical cap is removed and the carousels pass an explicit width, so the constraint sits with the layout that needs it. Favorites cards fill the row at every width.                                                                                   |
| **9. What does not change**                  | Home's carousels keep 270dp. The horizontal variant is untouched. No token changes.                                                                                                                                                                                       |
| **10. Migration risk**                       | **Medium, and higher than it looks** - not because the change is complex, but because there is no baseline. Search must be measured first, and RTL confirmed (the gap should mirror to the left edge, not vanish).                                                        |
| **11. ## Certification impact

> **Superseded 2026-09-01 by the D3 usage audit.** This section originally read
> "exactly one item blocks certification: D1", with D3 as a conditional. The
> condition was tested and it failed. **There are two blockers: D1 and D3.**

**Two items on this list block design-system certification: D1 and D3.** Both
are measured WCAG AA text failures on surfaces users reach, and an AA failure
cannot be accepted as an intentional exception.

**D2 is contested rather than failing** - a shortfall against 1.4.11 with named
compensating affordances. It needs a decision, not necessarily a change; what it
cannot stay is `UNRESOLVED` with no position recorded.

**D3 is now a blocker.** The audit in
`.claude/work/parcless-bag-palette-audit.md` classified all 14 occurrences of
the two colours by role and measured each against its real ground. **All 8 sage
usages are body text** on `bg-primary` at 3.23-4.02; terracotta carries body
text at 3.55 on cream and white text at 3.37-4.22 on itself. Its two
_background_ uses are fine at 3:1 - what fails is the text. **In dark mode
`bg-primary` inverts to `#54ACB6` while sage does not, putting six strings at a
ratio of 1.00.** The brand question D3 has always carried is still open and
still product-owned; the AA failure underneath it is not.

**D4, D5, D6, D8 and OfferCard width are not certification blockers.** They are
consistency, performance, brand and product questions. Treating any of them as a
blocker would be mistaking difference for defect.
