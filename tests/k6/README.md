# k6 performance & concurrency suite

Two kinds of test live here and they are deliberately kept apart.

| Directory   | What it is                                                                  |
| ----------- | --------------------------------------------------------------------------- |
| `journeys/` | Load tests. Model a _person_, carry think-time, assert almost nothing.      |
| `smoke/`    | Functional tests. Assert everything, no think-time. Not a perf measurement. |

Mixing the two is what made the previous suite unusable: assertions add latency
to a load test, and a functional test that reports p95 gets mistaken for one.

## Layout

```
config/      environments, thresholds (the single source of "too slow"), load profiles
lib/         http (forces the name tag), auth (token pool), envelope, summary, runner
journeys/    cold-start, browse, checkout, merchant-dashboard, driver-poll
suites/      gate, capacity, soak, spike, concurrency, rate-limit
smoke/       the original nine endpoint modules, unchanged
fixtures/    concurrency.json, regenerated by the seed script
```

## Running

```bash
# 1. bring up the stack (compose Mongo is a single-node replica set — see below)
docker compose up -d mongodb mongo-init redis backend

# 2. seed fixtures (200 consumers, 20 merchants, 500 offers, 50 scarce offers)
ALLOW_LOADTEST_SEED=true pnpm --filter @foodwaste/backend seed:loadtest

# 3. run a suite
k6 run tests/k6/suites/gate.js --env ENV=docker
```

On Windows, `.\tests\k6\run.ps1 gate` wraps this and runs the invariant verifier
automatically after the concurrency suite.

| Suite         | Where            | Fails build | Purpose                                    |
| ------------- | ---------------- | ----------- | ------------------------------------------ |
| `gate`        | docker (CI)      | yes         | per-endpoint latency regression            |
| `concurrency` | docker + staging | yes         | correctness under simultaneous requests    |
| `capacity`    | staging          | no          | find the breakpoint                        |
| `soak`        | staging          | no          | 2h — leaks, pool exhaustion, token refresh |
| `spike`       | staging          | no          | burst survival **and recovery**            |
| `rate-limit`  | anywhere         | yes         | asserts the throttler still fires          |
| `smoke`       | anywhere         | —           | post-deploy functional check               |

## Two things that will bite you

**The rate limiter.** `THROTTLE_LIMIT` defaults to 100 requests/minute per IP. A
load generator is one IP, so at production values a run collects 429s within
about three seconds and measures the throttler instead of the application. Every
environment used for load testing raises it. That is only defensible because
`suites/rate-limit.js` runs against real values and asserts the limiter fires —
if you delete that suite, you have quietly disabled brute-force protection
testing.

**Payments.** The checkout journey and the duplicate-webhook scenario need
`PAYMENT_PROVIDER=stub`. Otherwise the webhook's verification call goes to the
real Konnect API, fails, and returns early without settling anything — the test
passes while testing nothing. The stub is refused outright when
`NODE_ENV=production`.

## Thresholds are not yet calibrated

`config/thresholds.js` currently holds **estimates**, not measurements. They are
shaped by what each endpoint does, not by any observed run. Before treating the
gate as authoritative:

```bash
k6 run tests/k6/suites/gate.js --env ENV=staging   # three times
```

then set each entry to the measured p95 × 1.3 and record the date in that file.
Until then a pass means "nothing is catastrophically slow", not "no regression".

## Why compose Mongo runs as a replica set

Order creation, the payment webhook and several other paths call
`session.withTransaction()`, and MongoDB only offers multi-document transactions
on a replica set. Against the previous standalone configuration every one of
those paths failed with `IllegalOperation`, so checkout could not run locally or
in CI at all. One node provides no redundancy — this is purely about
transactions. `mongo-init` initiates the set idempotently and exits only once a
PRIMARY is elected, which is what the backend waits on.
